# BlockLocker 1.15-4 实施与验收计划

目标：核实报告后，仅优化 BlockLocker 的临时对象分配。Brewery 源码、JAR 和调用规则保留。
基线：c3477fc / BlockLocker-1.15-3；目标：BlockLocker-1.15-4，内部版本1.15。

1. 独立核对 Spark 原始文件、聚合结果、原JAR热点和原缓存/库存流程探针；复跑时不执行Brewery候选修改。
2. 先将两个Guava缓存替换为独立、重定位打包的Caffeine 3.2.4。容量各5000、初始1000、写后10秒；使用库默认的公共池合并维护，不创建插件专用线程或异步Bukkit loader。先保留Block键，单独验证分配变化。
3. 再将缓存统一为 World+x+y+z 不可变键。原Block公共入口保留；新增兼容default位置查询，第三方旧实现继续通过原Block方法工作。库存先查询位置，未命中仍调用原保护查找和回填；来源拒绝时不访问目标。负坐标、小数、跨世界及REDSTONE/GOLEM隔离回归。
4. 回归：TTL与写入刷新、同键/异键并发、满容量、允许/拒绝变化、reload重建及外部扩展、旧API实现兼容；重跑原15项测试。先看到旧版不能达到优化目标，再确认新版本通过。
5. 使用59603df准确核心、生产配置副本、PlugManX搭建仅绑定本机的隔离服。真实方块/牌子/库存、两区域并发、漏斗/投掷器/合成器/实体库存、锁规则、GC/热卸载检查。世界重载按准确核心能力处理，不能由测试夹具冒充实服。
6. 同一隔离服分别加载旧/新成品，在相同负载下采集分配与执行数据，报告本地事件/对象分配和生产采样权重推算；不把分配百分比宣传为整服CPU或MSPT提速。
7. clean verify、JAR独立校验、无官方更新器检查、重定位及依赖隔离校验；输出新JAR、完整源码ZIP、哈希、说明和测试记录。停止本次测试进程。保留生产输入和旧版回滚成品。

风险边界：Caffeine淘汰策略不同；高基数冷缓存可能增加位置键构造。命中负载与冷负载分别测量。保持原有10秒缓存状态窗口，不延长TTL，不增加长期Inventory缓存，不改变方块/实体调度所有权。

2026-11-17 实测裁定：同步维护原型在全冷4096位置负载中产生额外临时维护对象（TLAB申请量约+74%），因此最终改用Caffeine默认ForkJoinPool.commonPool合并维护。维护只处理缓存内部数据，不执行Bukkit查找；通过实际热卸载后GC检查验证任务完成后旧实例/类加载器回收。原型不作为最终成品交付，最终百分比重新测量。
